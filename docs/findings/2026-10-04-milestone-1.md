# Milestone 1: the first working bundler (2026-10-04)

`bundleup <project-dir | script.py>` now builds `dist/<name>.pyz` for the current platform and one
Python version. This write-up records how it fares against the gauntlet and the baseline tools,
and the measurements behind the design in [ADR-0010](../adr/0010-bundle-format-and-loader.md)
(format, loader, cache) and [ADR-0011](../adr/0011-cli-and-build-pipeline.md) (CLI, pipeline).

## Setup

- **Machine:** macOS arm64, the same machine as the [baseline](2026-10-03-baseline.md). uv 0.12.7.
- **Pythons:** macOS system Python 3.9.6 (`/usr/bin/python3`) and uv-managed CPython 3.12.14.
- **Correctness:** `uv run gauntlet/run_bundlers.py --tool bundleup --conditions`: every project
  except the heavy one, on both Pythons, network blocked, fresh `HOME`, empty working directory,
  plus the four hostile conditions. bundleup gets the project directory or script directly; the
  other tools got pre-exported requirements and pre-built wheels.
- **Speed:** `uv run gauntlet/bench.py 03 13 --python 3.12 --python 3.9` (new): one thing at a
  time, medians of 20 warm runs, 10 first runs (each with a fresh `HOME` and `TMPDIR`) and 3
  builds with warm caches. Installed venv (uv-synced, console script) as the floor. No
  `sandbox-exec`, since it isn't needed for timing.
- Raw results: [milestone-1-2026-10-04.md](../../gauntlet/results/milestone-1-2026-10-04.md)
  (generated) and [.json](../../gauntlet/results/milestone-1-2026-10-04.json);
  [bench-2026-10-04.json](../../gauntlet/results/bench-2026-10-04.json).

## Measurements behind the design

### Why two zips

Running a `.pyz` makes `zipimport` read the whole zip directory before `__main__` runs. A trivial
`__main__` in zips of increasing size (median of 30 runs):

| Entries | 3.9 | 3.12 |
|---|---|---|
| `python -c pass` | 14.2 ms | 8.7 ms |
| 1 | 20.5 ms | 9.5 ms |
| 1,000 | 22.8 ms | 10.7 ms |
| 5,000 | 31.3 ms | 16.3 ms |
| 20,000 | 63.4 ms | 36.0 ms |

About 1.5–2 µs per entry, on every start. PyTorch's 21,942 files would cost ~30–45 ms per run in a
flat zip (pex, shiv). bundleup's outer zip has three entries; the payload is one stored entry
read only on first run.

### Precompiled bytecode and the loader `.pyc`

Same builds with one feature removed (8 first runs, 20 warm runs):

| | 03 · 3.12 | 13 · 3.12 | 03 · 3.9 | 13 · 3.9 |
|---|---|---|---|---|
| Default: first run / warm | 48 / 29.1 ms | 571 / 38.8 ms | 142 / 40.3 ms | 857 / 51.6 ms |
| No precompiled payload | 79 / 30.3 ms | 621 / 40.7 ms | 161 / 40.0 ms | 896 / 51.0 ms |
| No `__main__.pyc` | 50 / 32.4 ms | 572 / 41.3 ms | 246 / 43.4 ms† | 995 / 52.2 ms† |
| Build cost of precompiling | +0.13 s | +0.40 s | +0.36 s | +0.60 s |
| Size with / without | 0.9 / 0.4 MB | 9.5 / 5.5 MB | 0.7 / 0.3 MB | 8.2 / 5.3 MB |

† measured before the `pycache_prefix` fix below.

Precompiling saves 20–50 ms on every first run, and is the only way a read-only cache gets
bytecode. It roughly doubles the size of a pure-Python payload. The loader's `.pyc` saves 2–3 ms
on every warm start.

### macOS system Python

On 3.9, precompiling first made **no difference**. The reason: Apple's `/usr/bin/python3` sets
`sys.pycache_prefix = ~/Library/Caches/com.apple.python`, so it never reads `__pycache__`
directories. Its standard library ships no `.pyc` either, so with a fresh `HOME` the first run of
*any* program compiles the stdlib modules it imports (~130 ms of the 3.9 first run for 03, for
every tool and for a venv alike). The loader now writes the payload's `.pyc` files under the prefix
when one is set (atomically, since the prefix is shared), which brought 03's first run from
236 ms to 142 ms in the variant runs.

### Build steps

`BUNDLEUP_TIMINGS=1 bundleup …` prints a breakdown. 03 on 3.12: find/probe Python 20 ms, export
11 ms, install 15 ms, compile 100 ms, zip 50 ms, loader compile + write 18 ms.

- **Compression level:** NumPy's 33 MB install: level 6 writes in 463 ms (9.5 MB), level 1 in
  183 ms (10.8 MB), stored in 24 ms (32.8 MB). Decompression is 37–39 ms either way. bundleup uses
  level 1.
- **Interpreter probe:** `uv python find /usr/bin/python3` costs 122 ms, and uv re-inspects that shim
  on every `uv pip install` (+120 ms) but caches the real interpreter. bundleup skips `find` for
  paths and uses the probed `sys.executable` afterwards. Importing `platform` in the probe cost
  33 ms on Apple's Python; it's no longer imported.
- **Compile workers:** a process pool is slower for small trees on macOS (spawned interpreters):
  03 on 3.9: 317 ms parallel vs 125 ms single; 13 (408 `.py` files) on 3.12: 184 ms parallel vs
  672 ms single. Threshold: 300 files.
- **PyTorch (20):** 14.5 s build, of which **11.3 s is zip compression** on one thread and 2.0 s
  compiling. This is bundleup's own work, so [ADR-0008](../adr/0008-prototype-in-python.md)'s
  speed trigger is relevant, but the fix isn't Rust: zlib releases the GIL, so compressing files
  on a thread pool (and writing the zip records ourselves) should cut it several-fold.

## Gaps and next steps

- **Not covered:** Linux and Windows runs (no Docker here; the loader's Linux/Windows cache paths
  and machine detection are untested), building for another platform, a conflicting package in
  user site-packages (the loader inserts before site-packages, so it should win, but this is
  untested), `pylock.toml` and `requirements.txt` inputs.
- **Parallel compression** for large payloads (PyTorch: 11 s of a 14.5 s build).
- **Cache cleanup:** old versions and interrupted `.tmp-*` directories accumulate.
- **`PYTHONPATH` leaks** to every child Python, not just `sys.executable`
  ([ADR-0010](../adr/0010-bundle-format-and-loader.md) consequences). Worth a gauntlet project:
  a bundle that runs a *different* Python as a child.
- **Pure-Python bundles are tied to one OS and Python version.** Relaxing that needs the analyzer
  to show no platform/version markers were involved.
- **The build-time analyzer** (`bundleup check`), the main differentiator, is untouched.
