# Baseline: existing bundlers vs. the gauntlet (2026-10-03)

The existing "needs only Python" tools, run against the [gauntlet](../../gauntlet/README.md) to find
where they fall short. Raw results: [baseline-2026-10-03.md](../../gauntlet/results/baseline-2026-10-03.md)
(generated) and [.json](../../gauntlet/results/baseline-2026-10-03.json).

## Setup

- **Tools:** pex 2.103.4, shiv 1.0.8, zipapps 2026.4.17, and "zipapp-naive" (what most people try
  first: `pip install --target` + stdlib `zipapp`).
- **Same inputs for every tool:** pinned requirements exported from `uv.lock` (or the PEP 723
  header), plus the project built as a wheel. Each tool used its documented approach for native
  code (`zipapps -u AUTO`).
- **Pythons:** macOS system Python 3.9.6 and uv-managed 3.12, on macOS arm64.
- **Runs:** network blocked (`sandbox-exec`), fresh `HOME`, empty working directory. Cold run, then
  warm run.
- **Hostile conditions** on every bundle that passed: path with spaces and non-ASCII characters,
  read-only working directory, read-only `HOME`, two simultaneous first runs.
- **Not covered yet:** running on Linux or Windows, and bundles built for another platform (no
  Docker on this machine); a conflicting older dependency already installed; pex's `--pylock`
  input.

### Hostile conditions (bundles that passed the base run)

| Tool | Spaces/Unicode path | Read-only cwd | Read-only HOME | Two first runs at once |
|---|---|---|---|---|
| **pex** | 37/37 | 37/37 | 37/37 | 37/37 |
| shiv | 37/37 | 37/37 | **0/37** | 37/37 |
| zipapps | 29/29 | **21/29** | 29/29 | **23/29** |
| zipapp-naive | 25/25 | 25/25 | 25/25 | 25/25 |

- **shiv** always extracts to `~/.shiv` and has no fallback: with an unwritable `HOME`, even hello
  world fails with a `PermissionError` traceback.
- **zipapps** unpacks native code into `./zipapps_cache` *in the current directory*, so it fails
  when launched from a read-only directory, and two simultaneous first runs collide
  (`FileExistsError`).

### Speed (Python 3.12, medians)

| | Build | Warm start (03, pure) | First run (03, pure) | First run (13, NumPy) |
|---|---|---|---|---|
| Installed venv (floor for comparison) | – | 59 ms | – | – |
| **pex (default)** | 1.8 s (11.8 s on 3.9) | **273 ms** | 649 ms | 1,559 ms |
| pex `--venv --sh-boot` | similar | 32 ms | 781 ms | 1,603 ms |
| shiv | 0.7 s (5.5 s on 3.9) | 69 ms | 106 ms | 691 ms |
| zipapps | 1.1 s | 97 ms | 102 ms | 660 ms |
| zipapp-naive (using uv) | 0.1–0.2 s | 89 ms | – | – |

- **pex by default adds ~210 ms to every start** compared with an installed venv. It can be very
  fast (32 ms) with `--venv --sh-boot`, but those aren't defaults, and an `--sh-boot` pex runs
  whichever `python3` is first on `PATH`: with macOS's 3.9 first, a 3.12 pex fails with
  *"Needed cp39-cp39-macosx_26_0_arm64 compatible dependencies … this pex had no 'click'
  distributions."*
- **pex on Python 3.9 resolves with a vendored pip 20.3.4 and its legacy resolver**, hence the
  slow builds.
- **Builds driven by uv take 0.1–0.2 s.** The tools that drive pip take 0.7–12 s.

### Error messages

Only one project should be refused (`17-modern-syntax` targeting 3.9). All four tools did refuse
it, but only because pip noticed `requires-python`. None said it plainly:

| Tool | What the user sees |
|---|---|
| pex | A multi-line pip command, then `pip: ERROR: Package 'g17-modern' requires a different Python: 3.9.6 not in '>=3.12'` |
| shiv | `Pip install failed!` |
| zipapps | A Python traceback ending in `RuntimeError: pip install failed: return code=1` |
| naive (uv) | A clear resolver explanation |

Without `requires-python` in the metadata, every tool would have produced a bundle that crashes
with a `SyntaxError` on the user's machine. None of them checks the code itself.

### Up-front diagnostics

**None.** Every failure in this run was discovered by *running* the bundle. No tool warned at
build time about `__file__` reads, dropped metadata, child processes, or silently lost compiled
extensions.

## What this means

### Answer to the open research question

> Does `__file__`/metadata breakage outnumber native breakage?

**It depends on the strategy.**
- **Tools that extract everything to disk (pex, shiv) avoid all three kinds**, at the cost of
  first-run time.
- **Tools that run from the zip hit file and metadata problems more than native ones.** zipapps
  handled every native project correctly (`-u AUTO`) but failed 5 projects (on both Pythons)
  on files and metadata. The research's claim holds for run-from-zip designs.

### The correctness bar is pex

pex passed every applicable project except one, and every hostile condition. Matching pex's
correctness is table stakes, and pex shows how: extract to a cache, keep metadata, use a fallback
cache location, extract atomically.

### Where we can be better (ranked by evidence)

1. **Fast by default.** pex is correct but adds ~210 ms to every run unless you know two flags,
   and those flags bring a `PATH`-dependent failure mode. Target: warm start at or below an
   installed venv, first run at or below shiv, with no flags.
2. **Fast builds.** Drive installation with uv: ~0.2 s vs pex's 1.8–12 s.
3. **Tell the user before they ship.** No tool warns about anything. A build-time check that flags
   `__file__` reads, metadata needs, child processes, version requirements (by parsing the code,
   not only trusting `requires-python`) and missing compiled extensions would have predicted every
   failure in this run.
4. **Errors in plain language.** "This project needs Python 3.12; you're targeting 3.9" instead of
   a pip log.
5. **Child processes work.** Make `sys.executable` children see the bundle's packages (zipapps
   does this; pex and shiv don't). One gauntlet project, but a common pattern in real tools.
6. **Robust caching without surprises.** Never write to the working directory; fall back when
   `HOME` isn't writable; extract atomically so simultaneous first runs are safe.
7. **Never degrade silently.** If a compiled extension can't load, say so.
8. **Read the files people have.** Every tool needed requirements exported and wheels built by
   hand first. Read `uv.lock`, `pylock.toml` and PEP 723 directly.

### Design consequences

- **Extract to a cache by default** (correctness), then optimise start-up. Run-from-zip is an
  optimisation the analyzer can enable per package when it's provably safe, not a default.
- **Cache location chain:** user cache dir → temp dir → next to the bundle; never the working
  directory. Extraction into a temp directory followed by an atomic rename.
- **Bootstrap does almost nothing on a warm start:** check version/platform, add one path, import
  the entry point. The 59 ms installed-venv number is the target.
- **Set `PYTHONPATH` (or equivalent) for child interpreters.**

## Next steps

1. Fill the coverage gaps: Linux (Docker or a CI runner), cross-platform builds (pex
   `--platform`), a conflicting site-packages install, pex `--pylock`.
2. Add gauntlet projects for patterns this run surfaced: a project with *no* `requires-python` that
   uses new syntax (would every tool ship a broken bundle?), a CLI that shells out to a
   dependency's console script.
3. Prototype the build-time analyzer against the gauntlet: can it predict every failure above
   without running anything?
