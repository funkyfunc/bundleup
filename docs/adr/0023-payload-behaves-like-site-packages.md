# ADR-0023: The payload behaves like a venv's site-packages: wheel executables stay, .pth files run

- **Status:** Proposed
- **Date:** 2026-10-05
- **Deciders:** an agent, while the user was away (roadmap item 10); needs the user's confirmation

## Context

[ADR-0010](0010-bundle-format-and-loader.md) puts the payload where a venv's site-packages would
be. Two differences from a venv broke real packages:

1. **The build removed `bin/`** to drop console-script launchers (they start the build machine's
   Python by its absolute path). But some wheels are mostly a program shipped as a wheel script:
   ruff, uv, ninja, cmake. Their Python wrappers look for the program in `bin/` next to the
   packages (the `pip install --target` layout), so `find_ruff_bin()` failed in a bundle.
2. **The loader ignored `.pth` files.** Python runs them in site-packages at start-up. setuptools'
   `distutils-precedence.pth` makes `import distutils` work on Python 3.12+ (the standard library's
   copy is gone); pywin32's adds the directories `win32api` lives in. In a bundle,
   `import distutils` raised `ModuleNotFoundError`.

pex and zipapps fail the first; pex, shiv and a plain zipapp fail the second
([learnings](../learnings.md), 2026-10-05).

## Decision

- **Only launchers are removed from `bin/` (`Scripts/` on Windows):** files there whose name is one
  of the distribution's own `console_scripts`/`gui_scripts` (plus `.exe`, `-script.py`,
  `-script.pyw`). Everything else a wheel ships stays, and the RECORD check expects it.
- **The loader processes the payload's top-level `.pth` files** the way `site.py` does: sorted,
  hidden ones skipped; `import` lines run, other lines append existing directories to `sys.path`;
  an error is reported on stderr and skips the rest of that file. The build lists the files in the
  loader's config (`PTH`), so bundles without any pay nothing.
- **Child processes** of the bundle's own interpreter process the `.pth` files too, `import`
  lines included ([ADR-0027](0027-children-see-the-bundle-only-from-its-own-python.md), 2026-10-07;
  before that they got only the directories).
- Tests: gauntlet [22-wheel-executables](../../gauntlet/projects/22-wheel-executables/gauntlet.toml)
  and [23-pth-files](../../gauntlet/projects/23-pth-files/gauntlet.toml) (pywin32 on Windows), and
  `tests/test_bundle.py::test_pth_files_are_processed_like_site_py`.

## Consequences

- Bundles that depend on binary-wrapping packages are bigger by the size of the binary (ruff:
  11.8 MiB bundle instead of 52 KiB); that's the program working instead of failing.
- A `.pth` file's `import` line runs before the app, as in a venv. That's code the lock already
  contains, so no new trust is involved.
- Children run the `.pth` files' `import` lines too, through the payload's `sitecustomize`
  (ADR-0027, as this ADR first anticipated).

## Alternatives considered

- **Keep dropping `bin/`, warn in `bundleup check`:** reports the breakage instead of avoiding it.
- **Call `site.addsitedir()`:** does the same processing but appends the payload to the end of
  `sys.path` and imports nothing new; the loader inserts the payload where site-packages was
  (ADR-0021) and would have to undo the append. Processing the lines directly is 20 lines.
- **Put `bin/` on `PATH`:** a venv doesn't either unless activated, and it would change which
  programs the app's subprocesses find.

## Evidence

- Gauntlet runs on 2026-10-05: bundleup passes 22 and 23 under every condition on Python 3.9 and
  3.12; pex and zipapps fail 22, pex, shiv and the plain zipapp fail 23.
